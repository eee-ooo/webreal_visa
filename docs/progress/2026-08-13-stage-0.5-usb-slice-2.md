# 阶段 0.5 USB provider/公共 API 切片记录

日期：2026-08-13

结论：第二个无硬件 USB 切片已完成。生产代码新增可替换 provider 注册/发现/打开边界和共享接口仲裁，将 USBTMC `INSTR` 接入公共 `viFindRsrc`、`viOpen`、读写、控制与取消路径；测试专用 provider/设备模拟器验证并发打开、拔出和重连。生产 libusb、USB488 完整控制、USB RAW 会话和真实硬件仍未完成，因此 `0.5` 保持进行中且硬件状态为 `NOT_TESTED`。

## 已完成

- `UsbProvider` 注册表按注册顺序取得强引用快照；发现结果经统一资源解析规范化、排序和去重，单个 provider 抛错不会隐藏其他来源。
- 每个 Resource Manager 在创建时保存不可变 USB 发现快照。拔出后旧 RM 的枚举不漂移，新 RM 反映当前发现结果；显式打开始终查询当前 provider 状态。
- USBTMC `INSTR` 经当前 provider 创建 `UsbTransport` 并进入既有 `UsbTmcBackendSession`；没有 provider 时返回 `VI_ERROR_NSUP_OPER`，有 provider 但资源不匹配时返回 `VI_ERROR_RSRC_NFOUND`。
- USB `RAW` 可被 provider 发现，但公共打开仍明确返回 `VI_ERROR_NSUP_OPER`，没有伪装未实现的 RAW 会话。
- `UsbInterfaceArbiter` 对同一连接代次与接口身份共享一次 claim；最后一个会话关闭时 release 一次，拔出可主动失效并立即 release，旧 lease 后续销毁不会重复 release。
- 模拟设备只存在于测试目标，没有将测试命令响应或虚拟设备行为放进生产库。

## 无硬件测试覆盖

- 公共 `viFindRsrc`：无效项过滤、大小写规范化、重复项去重、确定性顺序、provider 故障隔离和 RM 快照语义。
- 公共 `viOpen`/`viWrite`/`viRead`：USBTMC `*IDN?` 请求响应、终止符与 EOM。
- 公共 `viClear`、`viReadSTB`、`viAssertTrigger` 的 transport 能力委派。
- 两会话共享 claim，以及八个线程同时 `viOpen` 时仍只有一次物理 claim/release。
- 阻塞读取的 `viTerminate` 唤醒并返回 `VI_ERROR_ABORT`。
- 拔出使阻塞读取返回 `VI_ERROR_CONN_LOST` 并立即释放接口；重连后新代次可打开，旧会话继续保持连接丢失。

## 验证

- GCC 13.3 Debug/Release：完整 CTest 各 16/16，包含资源、API、并发、网络协议、ASRL、USBTMC 后端与公共 API、文档、ABI 历史和精确导出。
- GCC ASan/UBSan/LSan Debug：`detect_leaks=1`、遇错停止，完整 CTest 16/16；无 Sanitizer 报告。
- Release `usb_api_tests` 连续 1000 轮通过。每轮包含八线程同时打开、共享 claim/release、取消、拔出和重连，总计 8000 次并发会话打开无首次失败。
- Release 安装到全新临时前缀后，独立纯 C 静态/共享消费 2/2；安装产物仍严格导出 24 个既有公共符号，没有因内部 USB provider 增加 ABI。
- 文档契约通过，第一方文件地图覆盖 70 个受检文件；`git diff --check` 通过。

## 未完成与下一步

- 实现 USBTMC class-specific clear/abort 恢复状态机，以及 USB488 status byte、trigger 与 interrupt-IN 路径；先继续使用可故障注入 transport 做无硬件验证。
- 随后接入可选系统 libusb 1.0.30：固定来源/校验与许可、进程级事件 runtime、枚举匹配、真实 claim、异步 transfer、deadline、cancel callback 和拔出映射。
- 实现 USB RAW 的显式端点/control 配置与会话。
- Windows 原生和真实 USB 硬件验证仍须单独记录，模拟结果不能替代。
