# 阶段 0.5 生产 libusb 适配切片记录

日期：2026-08-13

结论：第四个无硬件 USB 切片已完成。项目现在可选动态链接 libusb 1.0.30，以生产代码完成 USBTMC/USB488 枚举、打开、共享 claim、异步 bulk/control/interrupt transfer、安全取消和热拔出映射；缺少依赖时其他后端与 USB 协议测试仍可构建。受控 libusb C API 模拟器已通过公共 `vi*` 覆盖完整适配边界，但本机没有可验证的 USBTMC 目标，因此真实 USB 硬件、驱动/权限组合与 Windows libusb runtime 仍为 `NOT_TESTED`。USB RAW 尚未实现，`0.5` 保持进行中。

## 依赖与构建边界

- 固定 libusb 1.0.30、标签 `v1.0.30`、提交缩写 `87a5563`。官方 `libusb-1.0.30.tar.bz2` 的 SHA-256 为 `fea36f34f9156400209595e300840767ab1a385ede1dc7ee893015aea9c6dbaf`。
- `WRVISA_LIBUSB=AUTO` 默认探测 1.0.30+ 头和动态库；找到时启用生产适配器，找不到时给出配置诊断并关闭。`ON` 缺依赖时直接配置失败，`OFF` 明确生成无 libusb 版本。
- `FindLibUSB.cmake` 从 `LIBUSB_API_VERSION` 校验最低版本并创建 `LibUSB::LibUSB`。项目不下载或复制 libusb 实现；CI 从校验后的官方归档临时构建动态库。
- 安装包携带 LGPL-2.1-or-later 原文和第三方声明。共享库动态链接 libusb；静态归档不含 libusb 对象。安装导出的静态/共享目标以 `LINK_ONLY` 恢复动态链接依赖，不传播 libusb 头文件到公共编译接口。

## 生产实现

- 内建 provider 扫描 active configuration，只接受 class `0xfe`、subclass `0x03`、protocol 0/1 的 USBTMC/USB488 interface；严格要求唯一 bulk-IN、bulk-OUT 和非零 bulk-IN 最大包长，可选唯一 interrupt-IN，并保留 alternate setting。
- 枚举读取 VID、PID、serial 与 interface，生成规范 `USB0::...::INSTR`；无合法序列号或畸形端点的 interface 不进入发现集合。显式打开按同一身份字段匹配，不用模糊设备路径替代 VISA 身份。
- 同一物理 interface 的多个会话共享 device ref、handle、claim 和连接代次。第一个 lease 执行 claim，最后一个释放时只 release/close 一次；到达/离开集合封闭了 claim 与热拔出并发窗口。
- 第一个物理 handle 启动专用 libusb event thread，最后一个关闭后停止。热插拔 callback 不执行 libusb I/O、描述符读取或阻塞工作，只记录 device pointer 和标记已有弱连接。
- bulk-OUT、bulk-IN、class control-IN 与 interrupt-IN 均使用 `libusb_submit_transfer`。每类端点独立串行，transfer timeout 来自 operation 剩余绝对 deadline；不同端点可独立推进。
- `viTerminate`/关闭在 active transfer 指针锁内调用异步 cancel，并等待 completion callback 后才清除指针及释放 transfer/缓冲，避免 cancel/free 竞争。NO_DEVICE 与热拔出映射为 `VI_ERROR_CONN_LOST`；旧连接不会因相同身份设备重连而复活。
- `libusb_clear_halt` 仅在对应 bulk endpoint gate 内执行，用于 USBTMC abort/clear 后的数据 toggle 恢复。权限、设备不存在、忙、超时、内存不足、不支持和普通 I/O 错误分别映射到可诊断 VISA 状态。

## 无硬件验证

- `libusb_provider_tests` 在启用/禁用两种构建中覆盖 interface/端点组合、USB488 标记、错误映射、发现结果规范化，以及不可能 VID/PID 的打开结果。
- `libusb_adapter_tests` 在真实链接官方动态库的测试目标中覆盖 libusb C API：规范枚举、两个公共会话共享一次 claim/handle、USBTMC `*IDN?`、USB488 状态字/interrupt-IN/trigger、class clear、异步取消 callback、abort-IN 恢复后复用、DEVICE_LEFT、连接丢失，以及最后一次 release/close。
- 模拟热插拔注册同时要求 ARRIVED/LEFT；DEVICE_LEFT callback 路径不调用任何 libusb API。待处理 transfer 由 event thread 完成 CANCELLED/NO_DEVICE，测试不会从回调线程提前释放资源。
- 本机实际枚举路径已运行，但没有发现可用于设备 I/O 的 USBTMC 目标；没有执行真实 claim、驱动 detach、权限失败或仪器查询，因此硬件状态保持 `NOT_TESTED`。

## 验证结果

- GCC 13.3、libusb 启用：Debug/Release 完整 CTest 各 18/18；GCC ASan/UBSan/LSan（`detect_leaks=1`、遇错停止）18/18，无 Sanitizer 报告。
- `WRVISA_LIBUSB=OFF` 全量 17/17，证明缺依赖分支不破坏其他后端和 USB 协议/provider 测试。
- Release `libusb_provider_tests` 连续 1000 轮；`libusb_adapter_tests` 连续 100 轮。后者首轮压力曾暴露测试设备“无数据立即返回空 EOM”导致等待活动 operation 的时序竞争；模型改为保持 bulk-IN 挂起后 100/100 通过。
- 前一切片的 Release `usb_tests`、`usb_api_tests` 各连续 1000 轮结果继续有效。
- Release 安装到全新临时前缀后，独立纯 C 静态/共享消费 2/2。消费测试发现共享目标最初只在自身 DT_NEEDED 中记录 libusb，链接器会选中同 SONAME 的旧系统库并缺少 1.0.30 符号；改为导出 `LINK_ONLY` 动态依赖后，两个目标均准确链接合格版本。
- ABI 历史与精确导出门禁通过，公共导出仍为既有 24 项；libusb/provider 类型均未进入公共 ABI。
