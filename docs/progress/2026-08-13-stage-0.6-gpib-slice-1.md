# 阶段 0.6 GPIB 第一切片记录

日期：2026-08-13

结论：第一个无硬件 GPIB 纵向切片已完成。标准 GPIB 资源身份现在贯穿解析、发现快照、provider 打开路由和后端会话；测试目标中的控制器通过既有公共 `vi*` 打通 EOI/read-ahead、能力控制、取消、超时和复用。生产库没有注册 linux-gpib、NI-488.2 或 Prologix provider，当前环境也没有真实控制器/仪器，因此本结果只证明受控内部契约闭环，真实 GPIB 和 Windows runtime 均为 `NOT_TESTED`。

## 资源与 provider 边界

- `ResourceDescriptor` 增加主地址、次地址和次地址存在标记；board 继续使用通用 `interface_number`，`INSTR`/`INTFC` 继续由资源类别区分。主/次地址范围仍限制为 0–30，并生成唯一 canonical name。
- `GpibProvider` 只返回标准 GPIB 资源名和项目自有 transport。发现阶段解析、规范化、排序和去重，单个 provider 抛出的异常不会隐藏其他 provider；每个 RM 保存创建时快照。
- 显式 `viOpen` 使用调用时的 provider 注册表。路由按注册顺序继续尝试，保存最早非“未找到”诊断；provider 返回成功但不给 transport 会转换为系统错误。
- RAII 注册令牌只属于内部 C++ 测试/后续适配边界，没有新增公共注册 ABI。`GPIB[board]::INTFC` 当前只解析和发现，打开明确返回不支持。

## Transport 与会话语义

- `GpibTransport` 不包含第三方头或句柄，读操作同时返回字节和 EOI，写操作显式接收 send-end；能力快照声明 device clear、trigger 和 serial poll 是否可用。
- 会话以一个 I/O 锁按半双工顺序执行读、写和控制事务；`cancel` 与 `close` 不取得该锁，仍能唤醒阻塞 transport。
- 读取先写内部缓冲，支持终止符、EOI、最大计数和 read-ahead。超时、取消或 transport 失败不会写用户缓冲，已取字节和 EOI 边界会恢复给下一次读取。
- 写入只有在 transport 报告完整计数并赢得 operation 完成竞争后才提交返回计数；transport 不支持 send-end 时，默认写入明确不支持，调用方关闭 `VI_ATTR_SEND_END_EN` 后仍可写。
- 具备能力时，`viClear`、`viAssertTrigger` 和 `viReadSTB` 分别映射到 device clear、trigger 和 serial poll；clear 成功与输入 discard 都会清理本地 read-ahead。

## 公共 API 测试闭环

- 测试 provider 发现 `GPIB7::4::2::INSTR` 与 `GPIB7::INTFC`，同时返回重复、非规范和非法名称，用于证明规范化、去重和过滤。
- 公共 API 覆盖 RM 创建前后 provider 注册造成的不可变发现快照、当前注册表打开、多个 provider 的发现故障隔离和延后诊断。
- 地址化会话覆盖 `viWrite`、终止符读取、EOI/read-ahead、`viReadSTB`、`viAssertTrigger`、`viClear`、`viFlush`、无限超时读取的 `viTerminate`、有限超时和取消后复用。
- 第二个 transport 关闭全部可选能力，覆盖 send-end、clear、trigger 和 serial poll 的明确不支持结果；模拟 provider 解除注册后，旧 RM 保留发现快照，但新打开明确不支持。

## ABI 与版本

- 工程、扩展头、实现版本属性、模拟身份和安装消费要求推进为 `0.6.0`。
- 本切片不新增函数、结构或常量；ELF 版本脚本仍只有 `WRVISA_0.1` 至 `WRVISA_0.5`，独立 ABI 清单仍固定 26 个现有公共符号。
- CI Release 稳定性集合加入 `gpib_tests`；文件地图、架构、兼容矩阵、需求、当前状态与 ADR-0010 同步更新。

## 当前验证结果

- GCC 13.3、libusb 启用：Debug 与 Release 完整 CTest 各 20/20；GCC ASan/UBSan/LSan 在 `detect_leaks=1`、遇错停止下 20/20，无 Sanitizer 报告。
- GCC 13.3 Debug、`WRVISA_LIBUSB=OFF` 完整 CTest 19/19，证明 GPIB 纵切及原有非 USB 代码不依赖生产 libusb 适配器。
- Release `gpib_tests` 连续 1000/1000 轮通过。取消场景会等待模拟 transport 确认读取已阻塞后再调用 `viTerminate`，不以线程调度近似后端状态。
- Release 全新安装后，独立纯 C 静态/共享消费 2/2；ABI 历史和 ELF 精确导出门禁通过，公共导出仍恰好 26 项。
- MinGW-w64 GCC 13 Release、`WRVISA_LIBUSB=OFF` 编译全部库和测试目标，包含新增 `gpib_tests.exe`；文档、ABI 历史和 PE 导出门禁 3/3，DLL 仍恰好导出 26 项。交叉产物没有运行，不能记为 Windows 原生 runtime 或 GPIB 通过。

## 限制与下一步

- 本切片没有生产 GPIB 控制器路径，最终用户尚不能用当前库直接访问物理 GPIB；测试 provider 也不会作为虚构硬件资源进入生产发现。
- 下一切片建议先评审 linux-gpib 用户库的 GPL 动态边界、board 配置来源、线程安全、`ibstop`/超时取消、错误状态和 descriptor 生命周期，再决定是否实现可选适配器及可注入 C API 模拟器。NI-488.2 和 Prologix 应保持为各自独立切片。
- 当前仅完成 0.6 的第一切片，不代表整个 0.6 代码范围收口，因此尚不触发“每完成一个 0.1 版本创建 Git 基线提交”的规则；0.6 完整范围收口并通过适用门禁后再提交对应基线。
