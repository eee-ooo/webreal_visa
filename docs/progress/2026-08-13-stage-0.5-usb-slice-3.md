# 阶段 0.5 USB class 恢复/USB488 切片记录

日期：2026-08-13

结论：第三个无硬件 USB 切片已完成。USBTMC `INSTR` 现在通过真实 class-specific control request 语义执行 clear、bulk-IN/bulk-OUT abort 和失败回退，并实现 USB488 GET_CAPABILITIES、状态字、TRIGGER 与 interrupt-IN 标签关联。脚本化 transport 和公共 `vi*` 模拟器均验证取消后同会话复用；生产 libusb、真实 USB 硬件和 USB RAW 仍未完成，因此 `0.5` 保持进行中，硬件状态仍为 `NOT_TESTED`。

## 已完成

- `UsbTransport` 暴露接口号、bulk/interrupt 端点、bulk-IN 最大包长，以及通用 class control-IN、interrupt-IN 和端点 halt 清除原语；协议层不依赖 libusb 类型。
- USBTMC 编解码新增 INITIATE/CHECK abort、INITIATE/CHECK clear、GET_CAPABILITIES、USB488 TRIGGER、READ_STATUS_BYTE control 响应和 interrupt-IN 状态包；严格拒绝错误长度、保留位、能力矛盾和无效标签。
- bulk-IN 解码按规范允许短包中最多 `wMaxPacketSize - 1` 个任意对齐字节，并以额外一字节接收预算区分合法最大对齐与缺少短包终止；bulk-OUT 仍要求四字节边界。
- `viClear` 执行 INITIATE_CLEAR/CHECK_CLEAR_STATUS，按 `BulkInFifoBytes` 排空至短包，成功后清除 bulk-OUT halt。
- 读写或 TRIGGER 被取消/超时时，原始 `VI_ERROR_ABORT`/`VI_ERROR_TMO` 结果保持不变；会话在独立 500 ms 预算内执行对应 bulk abort，失败时回退完整 clear。两级恢复都失败后关闭 transport，后续 I/O 返回 `VI_ERROR_CONN_LOST`。
- `viReadSTB` 缓存并校验 USB488 能力；无 interrupt 端点时直接使用 control 响应，有端点时用 2–127 的请求标签等待匹配包，同时消费 SRQ 标签和前一次请求的迟到响应；interrupt FIFO busy 映射为 `VI_ERROR_RSRC_BUSY`。
- `viAssertTrigger` 先校验设备能力，再发送 MsgID 128 TRIGGER；不支持能力返回 `VI_ERROR_NSUP_OPER`。

## 无硬件测试覆盖

- clear pending/成功、bulk-IN FIFO 排空和 bulk-OUT halt 清除。
- bulk-IN 取消、bulk-OUT 超时、abort pending/成功、abort not-in-progress 后 clear 回退，以及恢复后的会话复用。
- abort 与 clear 同时失败后的会话失效；畸形 clear/状态/interrupt 响应、错误能力组合和非法接口元数据拒绝。
- USB488 有/无 interrupt 端点状态字、SRQ、迟到标签、FIFO busy、trigger 支持/不支持和固定帧向量。
- 公共 `viTerminate` 取消阻塞 USBTMC 读取后，使用同一会话再次完成 `*IDN?` 查询。

## 验证

- GCC 13.3 Debug/Release：完整 CTest 各 16/16。
- GCC ASan/UBSan/LSan Debug：`detect_leaks=1`、遇错停止，完整 CTest 16/16；无 Sanitizer 报告。
- Release `usb_tests` 与 `usb_api_tests` 各连续 1000 轮通过，无首次失败。
- Release 安装到全新临时前缀后，独立纯 C 静态/共享消费 2/2；安装产物仍严格导出 24 个既有公共符号。
- 协议依据为 USB-IF `USBTMC_1_006a.zip` 内 USBTMC 1.0 与 USB488 1.0 规范；本切片没有引入或链接新第三方依赖。
